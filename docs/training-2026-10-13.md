# Two-day live Q3 onboarding handbook

Updated 14 October 2026 for onboarding in the week of 12-18 October. Participants will use the live database to enter their real Q3 2026 funding and expenditure. Q3 covers **1 July to 30 September 2026 inclusive**. Every confirmed submission contributes to live reporting. Use actual source amounts, transaction dates and references throughout.

The two days combine training with supervised completion of each MDA's Q3 return. Day 1 covers access, source preparation, reference requests and supervised manual entry. Day 2 covers AOP additions, discussion, corrections, audit trails, a readiness-gated AI import lab, offline capture and reconciliation. Participants leave with verified entry IDs and, where import is cleared, batch receipts and a list of unresolved source-data issues. It is not a dummy-data exercise. Do not insert invented amounts, test references or October transaction dates for July-September activity.

## How to use this handbook

Audience: MDA Users, Viewers (reviewers) and Admins. Suggested timing is **09:00-15:00 on each day**, including breaks; the facilitator may move the start time while preserving the practical work. Calendar dates are to be confirmed by the organizer. Pair each MDA submitter with a Viewer and keep an Admin available for access, reference and planning issues.

Each activity below names a result participants should demonstrate. Where no genuine transaction, correction, reference request or AOP addition is needed, inspect an existing record or complete the exercise on paper. Save only verified work that belongs in the live system. The supplied synthetic workbook is for the Day 2 import discussion or preview only; cancel its batch without inserting. If import remains unready, continue manual entry and assign file processing for follow-up.

Use the agendas first, then the numbered activities and field guides. The PDF also includes the offline runbook and a printable submission record. An unfinished return needs a named owner and follow-up date; attendance alone is not completion.

## What users can do today

Routine data entry uses two authenticated web forms: **Funding** for money received and **Expenditure** for money spent. Each submission records one transaction. Dropdowns use controlled reference data. The signed-in user supplies the audit identity; fiscal year and quarter come from the transaction date.

Valid entries become reportable when saved to the server. There is no approval or rejection queue. Comments ask for clarification without changing reportability. Publishing a quarterly Budget Implementation Report (BIR) locks new routine entries and edits for that quarter. Admin corrections after publication use an audited amendment.

Offline form submissions can be saved in this browser's local outbox and sent on reconnection. A pending local record is not yet a server submission or part of server reports.

**Imports → Import entries is available for CSV and XLSX transaction ledgers, but the AI import workflow is not yet fully ready for this training.** Day 1 uses the manual forms. On Day 2, the facilitator first checks the live draft flow with the synthetic workbook. The app can suggest workbook sheets, column mappings and meanings for unmatched values; users must verify each suggestion. Validation and insertion are separate confirmation steps. Use real-file insertion only after the technical owner clears insertion/receipt, the facilitator checks the live draft flow and the MDA owner reconciles its preview. If the readiness check is incomplete, defer live imports and continue manual entry. PDFs and planning/summary datasets (monthly returns, budgets, AOP, quarterly totals) are not accepted as transaction imports. The separate AI assistant remains read-only.

## Funding field guide

Open **Funding → New funding entry** (`/funding/new`). Check the default date before saving: use the actual July-September receipt date, not the October onboarding date.

| Field | Required | Meaning and rule |
| --- | --- | --- |
| Transaction date | Yes | Actual date funds were received. Enter a valid calendar date. |
| MDA | Yes | Select an MDA for which you have funding submission permission. A single assignment may be preselected. |
| Programme Area | Yes | Select the active programme classification. |
| Funding Source | Yes | Select the source of the money received, such as a government release, BHCPF or donor funding. |
| Amount | Yes | Nigerian naira, greater than zero. Use at most two decimal places. Commas are accepted by the form. |
| Reference Number | Yes | Actual source reference. Must be unique for this MDA and fiscal year within the funding ledger. |
| Remarks | Conditional | Optional unless Programme Area or Funding Source is Other. Explain any Other selection. |
| Fiscal year and quarter | Automatic | Derived from the transaction date; do not enter the year of today's data-entry session. |
| Entry ID, author and timestamp | Automatic | Created by the system. Keep the public entry ID for follow-up. |

Do not record an approved budget or a promised allocation as money received. Record receipts supported by the source, using the actual receipt date and reference.

## Expenditure field guide

Open **Expenditure → New expenditure entry** (`/expenditure/new`). Use the actual July-September payment date and check that the derived period is FY2026 Q3.

| Field | Required | Meaning and rule |
| --- | --- | --- |
| Transaction date | Yes | Actual date the expenditure was paid. |
| MDA | Yes | Must have expenditure submission permission for the selected MDA. |
| Money Amount | Yes | Total spent in naira, greater than zero. Use at most two decimal places. |
| Voucher Reference Number | Yes | Actual payment/voucher reference, unique for this MDA and fiscal year within the expenditure ledger. |
| Funding source breakdown | Yes | At least one actual funding source and positive allocation. Each source appears once; all allocations must equal the expenditure amount. The legacy Unspecified source is not allowed for new manual entries. |
| Payment Method | Yes | Select the method actually used: the configured bank transfer, cheque, cash, GIFMIS, IPPIS or Other option. |
| Programme Area | Yes | Select the relevant programme classification. |
| Expenditure Category | Yes | Select the spending category. A selected state-budget item can set and lock this classification. |
| Approved Budget Item | Optional linkage | Appears when a funding allocation uses the state-budget source. Select a matching MDA/year/class line where applicable. The current validator does not make this universally mandatory. |
| Expenditure Item | Optional | For non-state-budget classification, choose a configured item consistent with the selected category. |
| AOP Activity | Optional | If linked, must belong to the same MDA and fiscal year. |
| Remarks | Conditional | Required when Programme Area, Expenditure Category or Payment Method is Other. |
| Voucher attachment | Not ready for training | The UI accepts one image/PDF up to 10 MiB, but the route currently ignores the file argument. Do not promise that choosing a file saves it. |
| Fiscal year, quarter, entry ID, author and timestamp | Automatic | Derived or recorded by the system. |

Use the actual source allocation documented for the payment. All allocated amounts must equal the expenditure total. Splitting funding does not create two expenditure transactions. A single-source allocation follows the total amount automatically in the form. Payments funded from several sources should use this manual form; the current importer supports one funding source per expenditure row.

## Activity 1 - Understand and verify access

**Who:** Everyone, with Admin support. **Evidence:** Each participant records their role, allowed MDA(s), funding access and expenditure access on the submission record.

1. Sign in to your named account online. Identify the displayed role and available menus. Open Entry Register and check the MDA scope against your assignment.
2. An MDA User opens the permitted Funding and/or Expenditure form. Compare the available MDA choices with the assignment. Being able to view an MDA does not itself grant the right to submit both ledgers.
3. In the separate Viewer profile, open the register and reports. Explain statewide oversight and comments. In the standard Viewer setup there is no transaction entry/import or user-management workflow.
4. Admin opens **Users**, locates the participant and chooses **Manage**. Inspect the role and funding-entry/expenditure-entry MDA grants. Correct only actual approved access problems, then **Save access**. Participant reloads online or signs in again after first resolving any local queue.
5. Where a new participant needs an account, Admin demonstrates **Create a user** with full name, email, role and the appropriate grants. Choose email invitation or a temporary password delivered privately. Check the success/delivery result; a created account does not prove the invitation arrived. Manage also offers invitation resend and password reset for genuine access support.
6. Ask participants to explain why an unassigned MDA is unavailable and why knowing an entry link does not grant access. Do not change role or grants merely to create a classroom example.

**Access request to the Admin:** Provide your named email, requested role, MDA name, funding and/or expenditure duties, and the authorizing officer. Access requests use the organization's support channel; **Request a value** is for dropdown data, not user permissions. Do not include passwords in a request or entry comment.

**Check:** An MDA User identifies their scope, a Viewer finds an entry without editing it, and an Admin explains how role and ledger grants work together. Resolve missing access before assigning live entry work.

## Activity 2 - Request missing values and new fields

**Who:** MDA Users and Viewers prepare the need; Admin resolves reference requests. **Evidence:** A real request's label/type, status and follow-up owner, or a completed paper example when no change is needed.

First identify the kind of change:

| Need | Correct route | Example and result |
| --- | --- | --- |
| Another value in an existing dropdown | **Request a value**; Admin **Reference requests** | A verified funding source or expenditure item becomes selectable after Admin resolution. |
| Another AOP activity | Give the approved source row to Admin; **AOP activities** | An activity is added for the correct MDA/year, then linked to expenditure. Follow Activity 5. |
| An entirely new form field or report requirement | Record a development request through the agreed support channel | A new data column requires design, validation and implementation. Reference requests do not change the form schema. |

1. Search the existing dropdown first, including known names and abbreviations. Do not create a second label for the same underlying value.
2. Open **Request a value** (`/reference-requests`). Select **What needs adding?** and enter the exact **Value**. Supported kinds include MDA type, MDA, programme area, funding source, expenditure category/item, payment method, LGA and facility.
3. For an expenditure item, choose its parent **Expenditure category**; for a facility, choose its **LGA**. Add **Related MDA** where relevant and explain **Why is it needed?**, citing the source and intended use. AOP activities are not a reference-request kind.
4. Submit only a genuine request. Check it under your requests and note **Pending**. While it is unresolved, preserve the affected source row. Do not pick an unrelated value to force a save. Use Other only if it accurately describes the transaction, with the required remarks.
5. Admin opens **Reference requests** (`/admin/reference-requests`), checks duplicates and source evidence, then either approves using an existing value or creates the verified new value. A rejection requires a short explanation. Request approval applies to the dropdown request, not to financial transactions.
6. Requester reloads the request list, reads its status/comment and reloads the relevant entry form online. Confirm the resolved value is selectable and correctly classified. For an approved request linked to an existing value, use that canonical value. Do not assume an email notification or automatic update of an already open form.

**New-field request exercise:** Write the proposed field name, business purpose, data type/options, an example, who fills it, whether it is required and when, affected forms/imports/reports, treatment of old records, and source/owner. Give it to the facilitator for product/development triage. This is a proposed requirement, not an immediately available feature.

**Check:** Participants can distinguish a reference value, an AOP row and a new application field, and can explain how they will know their request is resolved.

## Activity 3 - Save and verify a real transaction

**Who:** Authorized MDA submitter; Viewer checks the result. **Evidence:** One public entry ID per genuine record entered, reconciled to its source.

Use the Funding and Expenditure field guides above. Both forms require an amount greater than zero; an absent return is not a zero-value transaction. Choose a previously unrecorded Q3 source transaction and confirm no one else owns its submission. For expenditure, show how the funding allocations sum exactly to the payment and how an applicable AOP/budget linkage is selected. Demonstrate required-field guidance before completing the actual record; do not change valid source facts to provoke errors.

Save once, read the result, open the saved record and refresh online. Verify date, FY2026 Q3, MDA, amount, reference, classifications and allocations against the source. Viewer finds the same public ID in a separate profile. A success message alone is not the reconciliation. If a save times out, search its reference before retrying.

**Check:** Participants distinguish the source voucher/reference from the system public entry ID, and can find the saved record again. Existing records may be reviewed when there is no outstanding transaction to enter.

## Admin planning data

Approved Budget forms require fiscal year, MDA, personnel, other recurrent and capital amounts. Amounts can be zero but cannot be negative. Recurrent and overall totals are calculated. The MDA/year combination is unique; an optional source label provides context.

AOP Activity forms require fiscal year, owning MDA, activity code, description and a non-negative budgeted cost. An optional source row number preserves legitimate repeated activity codes. Approved budgets and AOP costs describe plans; neither is evidence that cash was received or spent.

Reference data includes MDAs and their types, programme areas, funding sources, expenditure categories/items, payment methods, LGAs and facilities. During onboarding, create or update only genuinely required, verified reference values. Deactivate obsolete values to preserve history. Explain BIR publication using the screen and existing records; publish only when the real Q3 reporting process is complete and authorized.

## Activity 5 - Add to the AOP and link expenditure

**Who:** MDA planning/data officer supplies verified source details; Admin maintains AOP records; authorized submitter links expenditure. **Evidence:** Correct MDA/year/activity in the AOP list and, where applicable, on a genuine payment.

1. MDA officer locates the approved Annual Operational Plan source row. Prepare fiscal year, owning MDA, activity code, description, budgeted cost in naira, and source workbook/version/page or row. Confirm whether this is a missing approved row or a proposed plan revision. Obtain the normal planning authorization before asking for a revision to be recorded.
2. Admin opens **AOP activities** (`/admin/aop-activities`) and filters by fiscal year and MDA. Search existing activities, including inactive records where relevant. MDA Users cannot directly open this Admin management page; send the addition to the Admin through the agreed support process.
3. If genuinely missing, choose **Add AOP activity** and fill **Fiscal year**, **MDA**, **Activity code**, **Description** and **Budgeted cost**. Cost can be zero but not negative. **Source row number** is optional and distinguishes legitimate repeated codes from different source rows; do not use it to disguise an accidental duplicate.
4. Compare the draft with the approved source, then **Add activity**. For an actual correction to an existing plan row, use its **Edit** action and verify the source before **Save changes**. Inspect existing data or cancel the form if there is no real addition/correction to make.
5. Refresh the AOP list and confirm the result under the intended MDA and year. In the submitter's online Expenditure form, set the genuine transaction date and MDA, then find the matching **AOP Activity**. If missing, check MDA, fiscal year and active status before requesting another copy.
6. Select the activity for a relevant genuine payment, check all transaction fields, save and verify its details. If linking an existing payment, the ordinary edit/publication rules still apply. Adding an AOP row does not automatically link earlier expenditure or record funds received/spent.

**Check:** Participants explain that AOP cost is planned cost, expenditure is actual payment, and an approved budget is a separate planning record. Admin demonstrates the approved-budget MDA/year view where available; compare like-for-like periods and scopes instead of treating every plan total as cash available.

## Activity 6 - Discuss entries and verify comments

**Who:** Viewer and MDA submitter, in separate browser profiles. **Evidence:** A genuine question and response visible on the same entry after both profiles refresh, or a walkthrough of an existing discussion.

1. Viewer opens **Entry Register**, selects the correct Funding or Expenditure record and opens **Details**. Check public ID, reference, MDA, quarter and amount before writing.
2. Under **Comments**, enter a specific source-based question in **Add a comment or request clarification...**, then **Post comment**. For example, ask for confirmation of the actual date or allocation only when there is a genuine uncertainty. Avoid personal banking details or unrelated sensitive information.
3. MDA user opens the same entry and reads the question. Respond using the same comment box, identifying the question being answered. The current discussion is a flat list: there is no dedicated threaded Reply button, @mention workflow or demonstrated notification guarantee.
4. Both participants refresh online and check that the question and response remain, with the expected author, role and timestamp. Reopen the record from the register to confirm the discussion belongs to that record.
5. If a correction is needed, use Activity 7. A response or comment does not change the amount, the original **Remarks**, approval status or reportability. Remarks are part of transaction data; comments are the discussion alongside it.

Users discuss records they are permitted to access. An MDA user does not gain access to another MDA's entry merely because someone comments on it. Comments may continue after publication; they do not reopen the quarter. Do not promise comment edit/delete controls that are not present.

**Check:** The participant distinguishes a response from a financial correction and knows to reopen the entry to check for answers. Posting and refresh persistence were tested on live funding entry FL-2026-0001 on 14 October for both Viewer and MDA accounts. Two clearly marked training-test comments remain there; use them for a read-only demonstration if no genuine discussion is needed. This result does not establish that every ledger/role combination was tested.

## Activity 7 - Explain edit rights and audit trails

**Who:** Everyone inspects records; Admin handles reasoned corrections/amendments. **Evidence:** Each participant identifies an event's action, actor and time, and explains why a selected record can or cannot be edited.

1. Open a permitted entry's **Details** and inspect its author, transaction date, fiscal year/quarter and **Open quarter** or **Published** status. A transaction date is not the same as the date the user entered or changed the record.
2. Explain the Edit rule: before publication, an MDA submitter needs the relevant ledger grant and must be the original author. A colleague's row or a historical imported/aggregate row can have Details without Edit even within the same MDA. Admin can make open-quarter corrections with an audit reason. Viewer reviews/comments but does not routinely edit.
3. Inspect **Audit events**. The detail view lists event type, actor (or System), timestamp and a reason where recorded. Ask: what happened, who did it, when and why? An empty list means no events are available in this view; do not infer that no change ever occurred. The current panel is not a field-by-field before/after comparison.
4. If a genuine open-quarter error exists, the authorized owner or Admin opens the edit form, checks the source and saves the actual correction. Admin must enter an audit reason. A useful reason identifies the corrected field and source, such as a voucher/register reference; avoid generic reasons like "training". Do not manufacture an incorrect amount to demonstrate a repair.
5. Refresh the entry, confirm corrected values against the source and inspect the resulting audit information. Reconcile any amount change and let the Viewer verify the answer. If no correction is needed, inspect an existing event or cancel the edit form without saving.
6. Admin and Viewer open the **BIR** report for the intended fiscal year/quarter. Explain publication using its current state or an existing published quarter. Publication locks routine additions and edits for that FY/quarter across MDAs; comments do not unlock it. Keep Q3 open for the working session.
7. On an existing published record where available, Admin points out **Amend published entry** and **BIR amendment history**. An authorized amendment needs a reason and creates a new publication version. Do not execute one solely for demonstration, and do not promise a normal Unpublish button.

**Check:** Each participant can distinguish financial review, reference-request approval and BIR publication. Valid saved entries report immediately; a Viewer does not approve them. If a form still says "pending until a viewer acts", explain that this is stale wording. A genuinely pending offline record remains local until it synchronizes.

## Day 2 import procedure, after the readiness check

Use this procedure only if the facilitator has cleared the live draft-to-cancel workflow on Day 2, the technical owner has cleared insertion/receipt, and the MDA owner has verified the source. The importer accepts **UTF-8 CSV and XLSX, up to 10 MB and 5,000 data rows in the selected table**. Each batch imports one sheet/table of individual funding or expenditure transactions. A workbook may contain several sheets, but the user chooses one for the batch. Keep an unchanged original and prepare a working copy containing only the intended Q3 transaction data.

1. Open **Imports**, choose whether rows record Funding or Expenditure, select the file and press **Upload and inspect**. Uploading creates a private draft; it does not insert ledger records.
2. For a workbook, review **Workbook sheets** and select **Use this sheet** for the actual transaction table. Do not choose a dashboard, lookup, budget, monthly return or quarterly summary.
3. In **Map columns**, verify every suggested mapping against the sample values. If the file has no MDA column, select one permitted MDA only when every row belongs to it. Choose day-first or month-first interpretation for numeric dates based on the source. ISO dates such as 2026-07-15 avoid this ambiguity. Press **Apply and check rows** after changes.
4. Inspect **Ready**, **Blocked**, **Skipped**, **Excluded** and **All**. Correct genuine source errors using the row edit control and **Save and re-check**, or exclude unresolved/out-of-scope rows. A missing whole column must be added to the working file and mapped; do not invent values. Corrections in the preview preserve the uploaded original.
5. Check **Ready rows by quarter**: every included row for this exercise must be **2026 Q3**. The importer can accept other open quarters; it does not automatically restrict this session to Q3. Exclude accidental Q1/Q2/Q4 rows and verify Ready rows by MDA.
6. Reconcile the ready count and amount with the source records selected for insertion. Review hidden-row/formula warnings against the original. Acknowledge warnings only when the values are verified.
7. The submitter presses **Insert [count] funding/expenditure entries totalling [amount]** only when the displayed set is correct. Confirmation inserts ready rows into the live database and makes them reportable immediately. Blocked/skipped/excluded rows are not inserted. Their presence does not necessarily prevent confirmation of ready rows, so explicitly record any partial submission.
8. Read the receipt's committed count, amount and public entry IDs. Download **Issue report** and assign an owner to each unresolved row. Find the saved entries in the register and let the Viewer inspect them. A completed batch is immutable; remaining unresolved rows need a corrected follow-up file containing only outstanding transactions.

Funding imports require date, MDA (or a confirmed whole-file MDA), programme area, amount, funding source and reference number. Expenditure imports additionally require expenditure category, payment method and voucher reference, with one actual funding source covering the entire amount. Optional mappings include remarks, expenditure item and AOP code. The import mapping does not currently offer Approved Budget Item linkage; use the manual workflow when that linkage or split funding is needed.

An existing reference with the same date and amount can be skipped as already recorded. Compare its other details in the register as well; skip detection is not a full-field reconciliation. A reference with conflicting date/amount is blocked and never silently overwrites the entry. Use the normal correction workflow rather than assigning a new reference to the same transaction.

Repair damaged, oversized or unsupported files and upload a valid copy. Convert verified thousands/millions to naira; recalculate and save formulas without cached results. The importer never invents missing source facts or automatically repairs every corrupted file.

## Activity 8 - Practise import processing and AI suggestions

**Who:** MDA submitters with the relevant ledger grant; Viewers observe. **Evidence:** A reviewed synthetic workbook and, only if the readiness check passes, a cancelled practice draft. Live receipts are recorded only for separately verified real files.

The supplied file is **SYNTHETIC_Q3_Import_AI_Practice_DO_NOT_INSERT.xlsx**, in `output/training-dry-run/`. Read its **Read first** sheet. ## Facilitator FAQ

- **Why is Funding or Expenditure missing?** Check the relevant MDA grant, not just the role name.
- **Why is Edit missing on some rows?** Check publication state, original author and the relevant ledger grant. Viewing an MDA does not let you edit every entry.
- **Can I add a new AOP myself?** MDA Users prepare the approved source details; Admin uses AOP activities. MDA submitters can link a matching MDA/year activity on expenditure.
- **Does Request a value add a new form field?** No. It adds or resolves a controlled dropdown value. New form fields require a development request.
- **Where is Reply?** Responses use Post comment on the same record; the current list is not threaded.
- **Is a comment an approval?** No. Valid server submissions are already reportable.
- **Why is my saved offline row absent from reports?** It must sync successfully first; then reload the relevant list/report.
- **Why does an empty quarter show MDA reporting gaps?** A gap view can enumerate MDAs that have no returns. That is not evidence of transactions in that quarter.
- **Can I upload Excel on Day 1?** Keep real files for Day 2. The facilitator will verify the live CSV/XLSX draft flow first; if it is not ready, use manual entry and assign file processing for follow-up.
- **Is the importer AI-powered and can it read PDFs?** AI import is scheduled for Day 2 subject to readiness. When available, AI help is optional: **Analyze sheets with AI**, **Suggest mapping with AI** and **Suggest answers with AI** send column names, up to 8 sample rows or unmatched values to OpenAI and return suggestions you confirm. Validation and insertion stay deterministic. PDFs are not accepted yet.
- **Should I use today's date?** Only if that is the actual transaction date. This exercise is Q3 2026, so included receipts/payments must be dated 1 July through 30 September.
- **Can I import split-source payments?** Use the manual expenditure form for those; do not duplicate the voucher into separate imported rows.
- **Can I use the quarterly total as one transaction?** Only transaction evidence belongs in the transaction form. Period summaries must follow the appropriate aggregate data path.
- **Does a selected voucher file mean it was saved?** Not in this version. Attachment persistence needs implementation and verification.
- **Can we sign in for the first time offline?** No. Complete sign-in and load permissions/reference data online first.
